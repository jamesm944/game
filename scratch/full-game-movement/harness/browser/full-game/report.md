# Wayfinder #167 — asynchronous full-game real-browser evidence

## Verdict and evidence boundary

This directory implements an **asynchronous full-game browser driver** around the actual `World.step`, recorded commands/mutations, Activity queues, production group path continuation, individual stall repaths, steering, collision, and Parked/stall behavior. It uses the real production A* module Worker and the existing flow-field module Worker. It does not issue synthetic per-member searches.

Executed coverage is **headless Chrome 156.0.8078.47 on Apple M1 arm64, 16 GiB RAM**:

- A* dense 1,000 and mixed 1,000, 3,600 committed ticks;
- flow dense 1,000, 3,600 committed ticks;
- A* and flow narrow+mutation 100, 600 committed ticks, two measured repeats each;
- one warmup for every A* configuration and both mutation configurations; flow dense had no large-run warmup because of runtime. Each launcher configuration used a fresh page; every warmup and measured sample used a fresh worker.

The key ADR-0003 observation comes from the actual eight-group mixed A* order: **eight concurrent production leader requests had 39.4 ms response p95**, above 33.3 ms, while their production group/Activity application totaled **1.0 ms at the shared application tick**. This is an observed response-budget breach on one measured full-game trace, not a claim based on direct per-member stress. The subsequent real individual-repath stream had 121.0 ms response p95. Production apply p95 remained below 2 ms in the measured configurations; maxima are reported separately.

All five browser configurations matched their preserved same-candidate Node inline results in full logical comparisons and final full-state hash. Real async delivery changed frames and blocked counts, not committed simulation results. Firefox/WebKit remain unavailable, Safari automation remains disabled, and x64 remains unmeasured.

## Implementation and production fidelity

- `async-runner.ts` retains the existing runner's world/layer construction, deterministic group spawning, recorded `groupMove` commands, terrain/building mutations, completion tracking, crowd classification, milestones, and `BenchmarkResult` schema. The only execution-model change is `await yieldFrame()` after every attempted step, whether committed or blocked (`async-runner.ts:254-305`).
- Production `step` pumps due paths before incrementing the tick, draining commands, and running systems; a missing due response returns without advancing the world (`src/sim/core/world.ts:252-275`). The browser driver retries that same boundary after a `setTimeout(0)` macrotask, allowing actual worker messages to arrive. It never spins in a synchronous busy loop.
- The real movement system is registered unchanged. Initial group commands use one leader request and the production formation/member/Activity continuation (`src/sim/systems/movement.ts:599-686`). Later load comes from production individual stall repaths (`src/sim/systems/movement.ts:877-956`) and the real steering/collision/FSM loops (`src/sim/systems/movement.ts:1606-1807`).
- `worker-adapters.ts` constructs A* through production `createPathWorkerFactory()` (`src/game/paths.ts:10-29`) and flow through the existing `browser/flow.worker.ts`. Worker responses pass through the unchanged scheduler's ascending-ID, due-tick, stale-revision, and blocking contract (`src/sim/path/scheduler.ts:155-231`).
- Existing instrumentation times the actual requester `onApply` callback before harness bookkeeping (`harness/instrumentation.ts:96-154`). Thus leader apply cost includes the production group/Activity callback; individual apply cost is the production repath continuation. Worker-internal compute time is not guessed and is omitted from browser raw request records.
- Full-state milestones retain the original canonical `[tick, worldDigest, layersHash, serializedPrngState]` payload, hashed with browser `crypto.subtle` SHA-256 (`async-runner.ts:98-102`). Browser wall time includes event-loop yields and hashing; per-step wall time measures only synchronous `step(world)`.

`full-game-main.ts` runs warmups/samples, retains complete measured `BenchmarkResult` objects, and compares logical replays without wall timings or frame/queue samples. `replay.ts` covers milestones, completions, units, crowd states, movement diagnostics, mutations, and logical path/application records. `run-full-game.mjs` starts an ephemeral Vite server, launches Chrome/Chromium through Playwright, writes metadata/raw JSON, and closes all processes.

## Metric definitions

- **Initial leader:** request linked to a recorded command at tick 1. Dense has one; mixed has eight concurrently issued; narrow has two initial leaders whose responses become stale after tick-2 mutations.
- **Later leader:** recorded tick-180 narrow reissue. **Individual repath:** no command link; generated by production movement.
- **Issue→response wall ms:** actual transport send to real worker message receipt, including queueing, structured clone/delivery, search, and response delivery. Scheduler snapshot copying occurs before transport send and is not isolated.
- **Production apply ms:** actual group/Activity or individual-repath callback wall time. **Per-active-tick apply** sums all such callbacks applied at the same committed tick; percentiles include only ticks with apply work, making them conservative relative to including zero-work ticks.
- **Issue→apply ticks:** committed simulation boundary difference. It remains 2 even when real latency holds the target tick for additional frames. Blocked count, frame count, and wall milliseconds are separate evidence.
- **Payload:** summed scheduler snapshot bytes; every request carries a 14,400-byte 120 × 120 passability snapshot through actual structured clone.
- **Replay:** full logical result and production full-state hash, not merely route hashes. Cross-candidate A*/flow hashes are not required to match.

## ADR-0003 phase-2 interpretation

ADR-0003 describes phase 2 when concurrent leader searches push worker turnaround beyond one tick budget or production path application exceeds roughly 2 ms/tick (`docs/adr/0003-unit-movement-and-pathfinding.md:9-12,42,78`).

1. **Concurrent leader response:** the actual eight-leader mixed A* order measured 39.4 ms p95, exceeding 33.3 ms. This is direct full-game evidence of a response-side breach on that trace. Dense A*'s single leader was 30.6 ms and does not independently establish a concurrent-leader breach.
2. **Actual repath response:** A* individual-repath p95 was 110.9 ms dense and 121.0 ms mixed, with 716 and 744 blocked frames. This demonstrates additional real-worker pressure under production movement, but is reported separately from the ADR's leader-specific wording.
3. **Production apply:** mixed initial leaders totaled 1.0 ms at their application tick. Overall per-active-tick apply p95 was 0.1 ms for A* large traces and 0.4 ms for flow dense, below approximately 2 ms. Maxima of 2.4–10.7 ms are tail observations, not p95 breaches. Flow's single initial dense leader was 2.1 ms and is one quantized observation, not a sustained apply conclusion.
4. **Decision scope:** the mixed result supports the response side of the measured phase-2 trigger for this workload. One large sample per scenario is not a robust trigger distribution, and these results do not establish that flow is the best remedy. Flow's actual dense repath stream was substantially slower and blocked far more often in this integration.

## Remaining gaps and limitations

1. Only Chrome arm64 executed. Chromium was not needed for this slice; Firefox/WebKit remain unavailable, Safari remote automation remains disabled, and x64 remains unmeasured. No cross-browser performance or determinism claim is made.
2. Large scenarios have one measured sample each. Flow dense had no large warmup. Small p95 values over one or eight leaders are not stable timing distributions; repeated large runs are still needed.
3. Browser flow coverage is dense 1,000 plus mutation 100. Flow mixed/opposing and all browser 2,000-unit traces remain unmeasured.
4. The workload runs the real movement/placement loops but not combat, gathering, rendering, or a complete production session. Cutoff states are observed only at the recorded tick.
5. `setTimeout(0)` is an honest event-loop yield, not a 30 Hz render schedule. Total wall time includes timer clamping and browser scheduling; it is not simulated seconds and is not directly comparable with Node inline wall time as a pure compute benchmark.
6. Worker-internal compute, scheduler snapshot copying, and isolated structured-clone CPU are not separately measured. Flow worker cache/build telemetry is not transferred in this slice; raw route responses and full-game outcomes are measured.
7. Apply percentiles use Chrome's quantized timer. Per-active-tick aggregation excludes zero-apply ticks and is explicitly labelled; maxima include many callbacks sharing one tick.
8. Existing direct-load results and all Node raw results/reports are unchanged. This directory adds the full-game browser evidence path independently.
