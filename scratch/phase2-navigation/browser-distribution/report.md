# Wayfinder #168 — repeated real-Chrome full-game distribution

## Scope and verdict

This directory adds five fresh measured runs of the actual eight-concurrent-leader `mixed-destinations-120` order with production A*, 1,000 units, and 3,600 committed ticks. Every launcher invocation used a new headless Chrome browser and page, one warmup, and then one measured run; each run used a fresh real production worker. The workload executes the existing asynchronous `World.step` trace, including production group/Activity continuation, individual stall repaths, steering, collision, mutations, and Parked/stall behavior. It is not a direct per-member pathfinding stress substitute.

Executed environment: **Chrome 156.0.8078.47, Apple M1 arm64, 8 logical CPUs, 16 GiB RAM, Darwin 23.6.0, Node v24.21.0**. Browser automation was Playwright in headless mode. Chrome reported 0.1 ms `performance.now()` quantization.

**Response-side result:** 1 of the 5 per-sample eight-leader p95 values exceeded the 33.3 ms one-tick budget. The pooled 40-request initial-leader p95 was **48.0 ms**, also above 33.3 ms. This establishes observed response-budget breaches in this distribution, not a claim that every run breaches or a universal rate beyond this trace and host.

**Apply-side result:** no initial eight-group apply total exceeded approximately 2 ms (range 0.8–1.5 ms). No per-sample or pooled per-active-tick apply p95 exceeded approximately 2 ms: every p95 was 0.1 ms and pooled p95 was 0.1 ms. Tail maxima were 1.8, 1.9, 5.5, 1.8, and 2.8 ms; thus samples 3 and 5 had individual active-tick maxima above approximately 2 ms even though their p95 values did not. These are tail observations, not p95 apply-trigger breaches.

All five samples matched the preserved same-candidate Node mixed A* result in the complete logical replay comparison and final full-state hash. Firefox, WebKit, Safari, and x64 were not measured.

## Method and metric definitions

The runner reuses the existing full-game browser page without modifying it or its results. Configuration is exactly:

```json
{
  "candidate": "astar",
  "scenario": "mixed-destinations-120",
  "population": 1000,
  "ticks": 3600,
  "warmupRuns": 1,
  "measuredRuns": 1
}
```

- **Initial leader:** request with `commandTick === 1`. There are exactly eight per sample, all issued together by the real mixed order. Their responses apply together at tick 3 with issue→apply = 2 ticks.
- **Individual repath:** request without `commandTick`, generated by production movement.
- **Issue→response:** real transport send through worker response receipt, including queueing, search, structured-clone/delivery, and event-loop scheduling. Worker-internal compute and scheduler snapshot copying are not separately isolated.
- **Production apply:** the actual group/Activity or individual-repath callback. The initial-group value sums all eight callbacks at their shared apply tick.
- **Per-active-tick apply:** all production apply callbacks grouped by committed `applyTick` and summed. Percentiles **exclude zero-apply ticks**. Zero readings within active ticks are below timer resolution, not literally zero work.
- **Percentiles:** nearest rank, `sorted[ceil(p*n)-1]`. For n=8, p95 is the maximum; for the pooled n=40 leader set, p95 is rank 38. Eight leaders within a run are concurrent and correlated, and five runs remain a small distribution.
- **Replay:** `logicalBenchmarkString` compares milestones, completions, final unit rows, crowd states, movement diagnostics, mutations, and logical path/application records. Timing, response frames, and frame/queue samples are excluded; the final full-state hash is also checked explicitly.

Raw per-request records remain in each sample JSON. Derived leader timings are in `distribution.json`, and every derived active-tick apply row is in `apply-ticks.json`.

## Phase-2 threshold consistency

ADR-0003's phase-2 wording concerns concurrent leader worker turnaround beyond a one-tick budget or production path application above roughly 2 ms/tick.

1. **Leader response:** the pooled 40-request p95 of 48.0 ms exceeds 33.3 ms, and sample 1's per-run p95 of 48.6 ms also exceeds it. Samples 2–5 do not individually exceed it. This supports an observed response-side phase-2 condition in the executed distribution while showing that a single run is not a stable breach-rate estimate.
2. **Actual repath pressure:** pooled individual-repath response p95 was 115.5 ms, with 706–867 blocked frames per run. This is separate from the leader-specific trigger language.
3. **Production apply:** initial-group totals and per-active-tick p95 values do not exceed approximately 2 ms. Maxima of 5.5 and 2.8 ms in two samples are real tail observations but do not establish a p95 apply-side condition.
4. **Decision boundary:** these results do not establish that any particular alternative architecture is the best remedy, and they make no claim beyond the executed Chrome arm64 environment and this trace.

## Limitations

1. Five measured samples are still a small distribution. Each per-sample leader p95 has only n=8 and equals its maximum; the pooled n=40 is not a large-sample or breach-probability estimate.
2. Chrome's 0.1 ms timer quantization limits apply resolution. Displayed zero means below resolution, not no work; displayed decimal values are rounded from floating-point timer readings.
3. Only installed headless Chrome on Apple M1 arm64 executed. Firefox/WebKit/Safari and x64 remain unmeasured. The `MacIntel` browser platform string is not treated as x64 host evidence.
4. `setTimeout(0)` yields to the event loop but is not a 30 Hz render schedule. Total wall time includes browser scheduling and timer clamping.
5. The trace runs real movement/placement loops, not combat, gathering, rendering, or an entire production session. No extra candidates, populations, scenarios, browsers, or synthetic per-member stress runs were added.
6. No worker-internal compute, scheduler snapshot-copy, or isolated structured-clone CPU distribution is claimed. Snapshot bytes and end-to-end response/apply timings are retained instead.
